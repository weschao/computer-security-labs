Hardened Build & Crypto Verification

Hardened sender, responder, and checker built on a real HMAC-SHA256 — and proof that cryptographically secure computation runs comfortably on micro:bit hardware.

✓ Verified: yes, a micro:bit can do this.
The SHA-256 / HMAC-SHA256 shipped here reproduces the official FIPS 180-4 and RFC 4231 test vectors exactly, and a full protocol simulation confirms the design (seed secrecy, tamper rejection, relay rejection, replay resistance). It uses only Static-TypeScript features, so the same code compiles to native ARM on both micro:bit v1 and v2. And on v2 the crypto is literally in silicon.

Can the hardware really do it?

micro:bit v1  Nordic nRF51822

  • Arm Cortex-M0 @ 16 MHz · 16 KB RAM · 256 KB flash
  • Hardware AES-ECB block (the one the BLE radio uses)
  • Our software HMAC-SHA256 fits easily: a few hundred bytes of RAM, a few ms per operation

micro:bit v2  Nordic nRF52833

  • Arm Cortex-M4F @ 64 MHz · 128 KB RAM · 512 KB flash
  • Arm CryptoCell-310: hardware AES, SHA-256, ECC, and a true RNG
  • BLE uses hardware AES-CCM — authenticated encryption is a built-in silicon feature

In other words, secure symmetric crypto isn't a stretch for this chip — it's a hardware feature. MakeCode's high-level layer just doesn't expose the accelerator by default, so the code here implements HMAC-SHA256 in portable Static TypeScript. That's the strong result: even without touching the accelerator, a real MAC runs with time to spare. For a production build in C++/Zephyr you'd call the CryptoCell directly.

What "hardened" means, concretely

The protocol (one primitive, three uses)

1
Root of trust — a pre-shared cell key. Each cell agrees a 128-bit CELLKEY in person and loads it out-of-band. It is the one secret, and it never goes on the air.
2
Confidential seeding (encrypt-then-MAC). The sender ships the day key as C = DAYKEY ⊕ HMAC(CELLKEY, 0x00‖IV) with tag HMAC(CELLKEY, 0x01‖IV‖C). Eavesdroppers see only IV, ciphertext, and tag; a forged seed fails the tag.
3
Proof of knowledge (challenge–response). The responder answers HMAC(DAYKEY, 0x02‖nonce‖ownSerial), truncated to 12 bytes. Fresh nonce = no replay; HMAC = the answer leaks nothing about the key; serial binding = a relayed answer only ever credits the real device.
Domain-separation bytes (0x00 / 0x01 / 0x02) keep the three uses of the key cryptographically independent. Truncating HMAC to 12 bytes is standard and keeps every packet within the radio's 19-byte payload.

Net effect: the +5 now requires genuinely stealing a cell's key — which the crypto no longer hands over on the air. Confidentiality holds unless a device or a member is compromised, which is exactly the lesson you want left standing.

What this still doesn't fix (on purpose)

The pre-shared key must be loaded out-of-band. The sample keeps CELLKEY in the source for testing; in a real round it must be entered on-device (or provisioned separately) so it isn't in the code you submit publicly. This is the whole operational discipline — and the point of Kerckhoffs.
Endpoint compromise still wins. A USB flash dump or a borrowed unlocked device recovers the key regardless of how good the crypto is. Physical custody, PIN-lock, and zeroizing after the sweep are the answers — not more math.
Insiders still leak. Every member must hold the key to score, so any member can hand it over. Crypto can't repair a trust problem; smaller cells reduce the surface.
Randomness & timing. Math.randomRange is a software PRNG — for real nonces/IVs, pull the v2 hardware TRNG. And this teaching implementation isn't constant-time, so it isn't hardened against timing side channels (irrelevant at classroom scale, but worth naming).
We didn't authenticate the challenger — and showed we don't need to. Because HMAC is a PRF and responses are serial-bound, answering any challenger is safe: a relayed answer credits only the real device. If you wanted challenger authentication anyway, the v2 CryptoCell can verify the checker's ECC signature.
