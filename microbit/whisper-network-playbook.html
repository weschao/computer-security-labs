Attack & Defense Playbook

What your students will try, and how a group defends — mapped to the exact rules and scoring you specified. Each attack sits beside the defense that answers it.

The board

  • Start of class: you transmit each group's 128-bit key using that group's own software. Default starter code sends it full power, unencrypted.
  • Members may move freely but can't leave the room; devices stay in play the whole class.
  • Groups submit custom software for the next day — and all submitted software is made public.
  • Final 10 min: you sweep the room, challenging each device with a (groupID, nonce).
  • +1 for each of your members who answers your challenge correctly · +5 if any of your devices answers a different group's challenge.
Offense is subsidized. One cracked rival = +5, and a single device can hoard several groups' keys (+5 each). Your own defense tops out at group size (3–5). Expect an espionage-dominant meta — most effort will go into stealing, not hiding.
Code is public → Kerckhoffs's principle. Tomorrow everyone reads your source. Security can live only in the key, never in a clever secret algorithm. This also levels skill: weak coders can copy strong crypto, so the edge shifts to protocol design, physical play, and social moves.
The central tension. Since the algorithm is public, your only real secret is key material loaded out-of-band (not present in the code you hand in). But every member must know that key to earn its +1 — so every teammate is also a leak path. Confidentiality (few knowers) and availability (all must know) pull in opposite directions. Bigger groups score more +1s but expose more insiders.

1

Seeding — the opening broadcast

You transmit the key using the group's software. If that software is weak, you leak their key for them. Goal: only the group's own devices learn the key.
Passive sniff of the default broadcast RadioAccessible

Day 1 code sends full-power cleartext. Sit on each radio group in turn (radio.setGroup), log every packet to serial, read off every key. ~6 blocks.

Encrypt under an out-of-band key

Pre-share a group key in person before class; transmit only E(groupKey, dayKey). Eavesdroppers get ciphertext. This forces the real lesson: bootstrapping a secret channel.

Break home-made crypto CryptoAdvanced

A group invents a cipher (short-key XOR, LFSR, "reverse the bytes"). Because the source is public, it's a paper exercise to reverse it.

Use vetted crypto, secret only in the key

Use provided AES/HMAC blocks; never roll your own. Assume the attacker has your source — because they literally do.

Keystream / IV reuse (two-time pad) CryptoAdvanced

If the same keystream encrypts two messages, XOR the ciphertexts and peel them apart — no key needed.

Fresh random IV every message

Never reuse an IV/counter under one key; send the IV in the clear alongside the ciphertext.

Read the hardcoded secret CryptoAccessible

The Kerckhoffs trap: a group bakes its group key into the source as a constant — then submits the source publicly. Free key for everyone.

Keep secrets out of submitted code

Load key material out-of-band (typed in via buttons at class start, or provisioned by a separate program) so the public source contains none of it.

Spoof the seed source / force a re-send RadioAdvanced

Impersonate the instructor's transmitter to re-seed a victim with a chosen key, or replay a "send again" trigger to make them re-broadcast so you can capture it.

Authenticate the source; ignore re-seeds

Accept a key only from an authenticated sender; treat the day's seed as one-shot and refuse unsolicited re-transmission requests.

2

Propagation — getting it to every member

Every member needs the key for its +1, but each hop is a chance to leak or be blocked. This is confidential multicast to the member set — under everyone's noses.
Sniff an in-clear re-share RadioAccessible

Members who received the key relay it to a straggler in plaintext; a listener grabs it on the second hop even if the first was protected.

Encrypt every hop, not just the first

All peer-to-peer sharing uses the group key too. There is no "safe" internal broadcast.

Imposter "member" (Sybil) AccessAccessible

An outsider device claims to be a groupmate to be handed the key. If membership isn't checked, the key walks out the door.

Mutually authenticate membership

Prove group membership (possession of the group key) before sharing anything; challenge–response both directions.

Man-in-the-middle a peer exchange CryptoAdvanced

Relay a two-device key setup, sitting invisibly in the middle and learning what passes through.

Compare an authentication string

After a peer exchange, verbally compare a short fingerprint in person; a mismatch reveals the man in the middle.

Jam a member off the air DenialAccessible

Flood a radio group so one teammate never receives the key and loses their +1. Cheap and requires no cryptography at all.

Redundancy + physical fallback

Multiple members can re-seed each other; add retries and hop radio groups; if all else fails, huddle and re-share at arm's length.

Turn a member (insider leak / defection) InsiderAccessible

The key must live in every teammate's head/device. Bribe, befriend, or collude with one of them and confidentiality is gone — no packets intercepted.

Minimize and compartmentalize (imperfectly)

Keep the raw key on devices, not spoken aloud; run smaller groups to shrink the insider surface — accepting fewer +1s in exchange. There is no clean fix; that's the point.

3

The Sweep — proving it, and stealing the +5

Fresh nonces mean a device must actually compute a response, so an attacker needs the key — or a victim device willing to compute for them. This phase is where the +5 is won.
Answer with a stolen key (+5) CryptoAccessible

Any key captured in Phase 1–2 lets your device compute HMAC(theirKey, nonce) on the spot and claim the +5. This is the whole payoff of espionage.

(As victim) never let the key escape

Everything in Phases 1–2, plus zeroize the key once your own sweep is done so a late theft is worthless.

Relay / wormhole attack (+5, no key!) ProtocolAdvanced

You never learned the key. During the sweep you relay the instructor's challenge to a victim's device, get its answer over radio, and present it as your own. Possessing a willing signer ≈ possessing the key.

Don't be a signing oracle + distance-bound

Only answer a challenger you've authenticated (the real Checker), and enforce a tight response deadline so a relayed round-trip is too slow to pass.

Signing-oracle abuse ProtocolAccessible

If a victim's device will compute a response to any nonce from anyone, just ask it. A naive "reply to every challenge" loop hands out proofs to rivals.

Authenticate the challenger; lock after use

Respond only to the authenticated Checker; rate-limit; go silent once the legitimate sweep has scored you.

Predict the nonce → precompute / replay CryptoAdvanced

If nonces are weak or repeat across days, record a victim's answer and replay it, or precompute responses ahead of the sweep.

Use the full, fresh nonce every time

Bind responses to the complete instructor nonce; never cache or reuse a response. (Relies on the instructor issuing strong, unpredictable nonces.)

Guess / forge a weak response CryptoAdvanced

If the response is a short or truncated code, the answer space is small enough to guess in the time allowed.

Full-length standard MAC

Use a full HMAC output so forgery/guessing is infeasible.

Borrow / steal a victim device AccessAccessible

Grab an unattended device during the sweep so it answers for you, or clone its key. Movement is allowed and devices can't leave — so they're all within reach.

Physical custody + lock + zeroize

Never set the device down; PIN-lock the response action; wipe the key immediately after your own sweep.

Spoof device identity to misattribute AccessAdvanced

Confuse the Checker's attribution so a response is credited to the wrong device/group, or inject responses on another group's behalf.

Signed, identity-bound responses

Responses include an authenticated device identity so the Checker credits the right device; the Checker verifies who actually answered.

Attacks on the rules themselves

A security mind attacks the scoring, not just the crypto. These are the loopholes a "creative, deviant" student will find first — with patches if you want to close them.

Cartel collusion

Two groups quietly swap keys. Each now answers the other's challenge → both bank +5, and (if scoring is absolute) neither loses anything. Cooperation beats security.

Patch: make a leak cost the victim — e.g., −5 whenever any foreign device answers your challenge. Now swapping keys is a prisoner's dilemma, not a free win.
The master-spy device

One device hoards four groups' keys and scores +20 in a single sweep. Offense scales without bound; defense caps at group size.

Patch: cap espionage points per group per day, or scale defense to match (e.g., a "clean sweep — no foreign device answered us" bonus) so hardening pays off too.
Poisoned public code

Publish "improved, faster" software with a subtle backdoor (leaks the key on a hidden trigger, or a predictable RNG seed), hoping rival groups adopt it — then harvest everyone who did.

Patch: reward it! Treat it as a supply-chain lesson: any code you adopt, you must review. Bonus points for the group that spots a planted backdoor.
Griefing by jamming

If standings are relative, blanket-jamming the room near the deadline suppresses rivals' +1s and lifts you without any theft.

Patch: decide up front whether scores are absolute (jamming is pure vandalism, easy to rule out) or ranked (jamming is rational — then build in jam-detection as a defended threat).

What each move quietly teaches

Kerckhoffs's principle

Public code forces security into the key alone. Home-made ciphers die on day two.

Out-of-band key exchange

You can't bootstrap a secret over a watched channel — the in-person key swap is the whole ballgame.

Don't build an oracle

Authenticate who's asking. A device that signs for anyone is as good as leaked, even with perfect crypto.

Relay & distance bounding

Proximity isn't presence. Timing bounds are how real contactless systems resist relays.

Nonces & replay

Freshness is why a recorded proof can't be reused — and why weak randomness is fatal.

Insider threat & economics

The people you must trust are your biggest risk, and attackers follow incentives — defend the branch that pays them, not the one that's fun to build.

Two design knobs worth deciding before day one: (1) Absolute vs. ranked scoring — it flips whether jamming and griefing are rational. (2) Allow out-of-band provisioning (typing/loading a secret onto devices outside the public source) — without it, the public-code rule makes confidentiality literally impossible, and the game collapses into "everyone reads everyone." Allowing it is what makes real defense possible.
